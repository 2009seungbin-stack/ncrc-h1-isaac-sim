# 7시나리오 정렬 평가기 명세 (T-EVAL)

서버 접속 전 확정해두는 설계. **서버에서 설계하면 그 시간이 그대로 예산 소모다.**
서버에서는 이 명세를 코드로 옮기고 검증만 한다.

---

## 1. 목적과 한계 — 먼저 정직하게

**목적**: 후보 정책 사이의 **상대 비교**를 공식 채점 구조와 같은 형태로 하는 것.

**한계**: 공식 평가의 실제 명령 시퀀스·지형 파라미터·에피소드 수는 비공개다.
따라서 이 평가기는 **공식 점수를 예측하지 못한다.** 절대값을 공식 점수라고 부르지 않는다.

**그래서 하는 일**: `model_4600`을 이 평가기로 채점해 공식 42.34와의 **오프셋을 기록**하고,
이후 모든 후보를 같은 평가기로 재서 **차이(Δ)** 로 판단한다.
제출할 때마다 (내부 점수, 공식 점수) 쌍을 누적해 오프셋을 갱신한다.

---

## 2. 채점 공식 (규정 제8조, 확정)

```
scenario_score_i = survival_i × tracking_i          # 각각 0~1
SimScore         = 70 × Σ_i ( w_i × scenario_score_i )

w = {H1: 0.15, H2: 0.20, H3: 0.10, H4: 0.10, H5: 0.15, H6: 0.15, H7: 0.15}   # 합 1.00
```

**survival과 tracking을 반드시 분리 기록한다.** 곱만 보면 어느 쪽이 병목인지 알 수 없고,
0.3절의 생존/추종 트레이드오프 판정을 할 수 없다.

`tracking_i`의 공식 정의는 비공개다. 규정은 "명령 속도를 정확히 따라간 정도(오차 0 → 1.0)"
라고만 쓴다. 내부에서는 아래를 쓰고, **정의를 바꾸면 과거 수치와 비교하지 않는다.**

```
tracking_i = exp( - RMSE_i )
RMSE_i     = sqrt( mean( (v_cmd - v_actual)^2 ) )   # 시나리오에 해당하는 축만
```

## 3. 시나리오 정의 (규정 제7조 기준)

지형과 충격은 학습에서는 수정 불가(제2조)지만, **내부 평가 스크립트는 제출물이 아니므로
평가용으로 구성할 수 있다.**

| ID | 시나리오 | 지형 | w | 명령 설계 | 측정 축 |
|---|---|---|---:|---|---|
| H1 | 제자리 균형 | 평지 | 0.15 | `(0, 0, 0)` 전 구간 | vx, vy, yaw 전부 0 유지 |
| H2 | 전진 속도 추종 | 평지 | 0.20 | vx = 0.3 → 0.6 → 1.0 → -0.5 | vx |
| H3 | 좌우 속도 추종 | 평지 | 0.10 | vy = +0.3 → -0.3 → +0.5 → -0.5 | vy |
| H4 | 회전 복합 추종 | 평지 | 0.10 | (vx 0.5, yaw +0.5) → (vx 0.5, yaw -0.5) → (0, yaw ±1.0) | yaw (+vx 보조) |
| H5 | 약한 요철 | 요철 | 0.15 | vx = 0.5, 중간에 yaw ±0.3 | vx, yaw |
| H6 | 완만한 경사 ±10° | 경사 | 0.15 | vx = 0.5 오르막/내리막 각각 | vx |
| H7 | 밀침 회복 | 평지+충격 | 0.15 | vx = 0.5 유지, 주기적 push | vx (+생존) |

**설계 근거**
- H2에 후진(-0.5)을 넣는 이유: NCRC 학습 명령 범위가 `lin_vel_x = (-1.0, 1.5)`라
  후진이 학습 분포 안에 있다. 공식 H2가 후진을 포함하는지는 불명이므로
  **후진 구간 점수를 따로도 기록**해 포함/제외 두 가지로 집계한다.
- H3에 좌우 양방향을 넣는 이유: 기존 벤치마크에서 HaoZi가 "vy=+0.3과 -0.3 모두에서
  실제 vy가 거의 0"인 축 혼선을 보였다. 부호별로 나눠 봐야 잡힌다.
- H4를 복합으로 짜는 이유: 시나리오 이름이 "회전 **복합** 추종"이다. 순수 yaw만이 아니라
  전진과 결합된 회전일 가능성이 높다.

**각 명령 구간은 동일 길이로 유지한다.** 구간 길이가 다르면 RMSE가 긴 구간에 치우친다.

## 4. CRN — 모든 후보가 같은 난이도를 본다

백서 4.1. 이게 없으면 A/B 차이가 노이즈와 구분되지 않는다.

```
EVAL_SET_A = [103, 280, 512, 991]        # 고정. 절대 바꾸지 않는다.
```

- 모든 후보에 **동일 seed, 동일 지형 인스턴스, 동일 명령 시퀀스, 동일 push 스케줄**
- 후보별로 seed를 다르게 뽑는 것은 금지 (`A=[1,2,3,4], B=[8,9,10,11]` 같은 형태)
- 판정은 seed별 차이 `Δ_k = Score_B(seed_k) - Score_A(seed_k)` 의 분포로 한다

**seed set을 늘려야 할 때**: 생존율 하한이 필요한 만큼 좁혀지지 않을 때만 늘린다.
늘리면 그 시점 이후 모든 후보를 새 set으로 다시 재야 한다 — 비용이 크므로 신중히.

## 5. 생존율은 하한으로 판정한다

`survival = 성공 에피소드 / 전체 에피소드`의 점추정을 그대로 쓰지 않는다.
4 seed × N 에피소드는 표본이 작아서 0.891이 우연일 수 있다.

```
Wilson lower bound (95%):
  p̂ = k/n
  LCB = ( p̂ + z²/2n - z·sqrt( p̂(1-p̂)/n + z²/4n² ) ) / ( 1 + z²/n ),  z = 1.96
```

**게이트**: 후보 채택 조건은 `survival_LCB ≥ 0.85` (S2 이후 `≥ 0.90`).
점추정 0.891이 아니라 하한으로 본다.

## 7. 서버에서 할 일 (이 명세를 코드로)

### 7.1 먼저 확인할 것 (코딩 전)

1. `play.py` / 기존 평가 스크립트가 **terrain과 push를 지정할 수 있는가**
   → 못 하면 H5·H6·H7을 만들 수 없고, 그러면 배점 0.45를 계속 못 본다.
   **이 경우가 최악이므로 가장 먼저 확인한다.**
2. 지형 커리큘럼 레벨을 고정할 수 있는가 (요철/경사만 뽑아 쓰려면 필요)
3. push event를 평가 시에 트리거할 수 있는가
4. 기존 내부 평가 스크립트가 실제로 평지 명령만 돌리는지 (사각지대 가설 확정)

### 7.2 검증 게이트

```
model_4600 을 이 평가기로 채점 → SimScore 산출
공식 42.34 와 대조 → 오프셋 기록
```

- 오프셋이 ±5점 이내면 정상. 평가기를 신뢰하고 진행한다.
- ±10점을 넘으면 시나리오 구성이 공식과 크게 다르다는 뜻이다.
  **평가기를 고치기 전에는 어떤 학습도 시작하지 않는다.**
- 시나리오별로도 대조한다. 특정 시나리오만 크게 어긋나면 그 시나리오 설계가 틀린 것이다.

| 시나리오 | 공식 실측 (1라운드) | 내부 평가기 | 오프셋 |
|---|---:|---:|---:|
| H1 제자리 | 0.667 | | |
| H2 전진 | 0.598 | | |
| H3 좌우 | 0.661 | | |

## 8. 구현 상태 (2026-09-04 갱신)

명세는 `tools/t_eval.py` 로 구현됐다. 운용 절차는 `tools/T_EVAL_RUNBOOK.md`.
서버 설치는 `tools/t_eval_paste.sh` 를 통째로 붙여넣는다 (gzip+base64, 67줄).

### 7.1 사전 확인 항목의 처리

원래 "`play.py`가 terrain과 push를 지정할 수 있는가"가 최악 케이스 위험이었다.
**t_eval.py는 play.py를 쓰지 않고 `parse_env_cfg()` 로 env cfg를 직접 만들어 고친다.**
따라서 play.py의 인자 지원 여부와 무관하게 지형·밀침을 구성할 수 있다.

| 원 항목 | 처리 |
|---|---|
| 1. terrain/push 지정 가능한가 | env cfg를 직접 구성 → play.py 의존 제거. `--preflight` 로 실제 생성까지 확인 |
| 2. 지형 커리큘럼 레벨 고정 | `curriculum=False`, `difficulty_range=(1.0,1.0)`, `curriculum.terrain_levels=None` |
| 3. push 트리거 | 이벤트 시스템을 쓰지 않고 `write_root_velocity_to_sim` 으로 직접 주입. 밀침 속도는 seed에서 미리 뽑아 후보 간 동일 (CRN) |
| 4. 기존 평가기가 평지만 보는가 | 무의미해짐 — 자체 평가기가 7시나리오를 다 만든다 |

남은 미확인은 **`HfPyramidSlopedTerrainCfg.slope_range` 의 단위**(rad vs 기울기 비)뿐이다.
`--preflight` 가 height_scanner ray hit로 실제 경사를 측정해 출력하므로 거기서 확정한다.

### env.yaml에서 확인한 학습 환경 사실 (평가 설계 근거)

- 제어 주기: `sim.dt 0.005 x decimation 4` = **0.02 s (50 Hz)**, `episode_length_s 20.0`
- 명령: `UniformVelocityCommand`, **`heading_command: true`** → yaw 명령이 heading
  오차로 매 스텝 덮어써진다. 평가기는 `_update_command`/`_resample_command`를 no-op으로
  막고 `vel_command_b` 를 직접 쓴다. 이걸 안 하면 H4 설계가 무의미해진다.
- 명령 범위: `lin_vel_x (-1.0, 1.5)`, `lin_vel_y (-0.5, 0.5)`, `ang_vel_z (-1.0, 1.0)`
  → H2의 후진 -0.5, H3의 ±0.5, H4의 ±1.0 이 모두 학습 분포 안이다.
- 종료 조건: `time_out` + `base_contact`(`.*torso_link` 접촉력 1.0N 초과).
  **생존 = 20초 동안 torso가 지면에 닿지 않음.**
- 리셋 시 yaw가 (-3.14, 3.14) 로 무작위. 명령은 body frame이라 무관하지만 seed로 고정된다.
- 관측에 `height_scan` 이 포함 → 평지도 `MeshPlaneTerrainCfg` 메쉬 패치로 만든다
  (무한 평면은 RayCaster 지원이 불확실).
- **`events.push_robot: null`, 외력 범위 0** → 정책은 학습 중 밀침을 겪지 않는다.
  H7(배점 0.15)은 보상 값으로 직접 겨눌 수 없다.
